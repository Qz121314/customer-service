# Customer Service

面向个人运营者和小团队的轻量客服坐席与咨询流量分发系统，独立于 [`Qz121314/site`](https://github.com/Qz121314/site) 开发和部署。

> 这个项目不是长期 CRM。核心职责是把 Site / 产品页产生的有效咨询，按产品负责范围、账号启用状态、每日接待上限、已购买咨询额度、CTA 两小时绑定和严格轮询，稳定地分配给具体客服，并提供 24 小时临时聊天接待能力。

生产地址：<https://customer-service-app.fcqz121314.workers.dev>

## 1. 系统边界

完整链路：

```text
Site / 产品页
→ 生成临时访客与唯一 sourceHandoffId
→ customer-service 校验产品上下文与防滥用规则
→ 根据负责范围、账号启用状态、每日接待上限和剩余咨询额度筛选客服
→ 有效 CTA 两小时绑定客服优先
→ 其余候选按严格 round robin 选择
→ D1 单条原子写入完成分配
→ 客服坐席工作台接待
→ 生成可统计、可对账的有效流量凭证
```

系统分为三个边界：

- Site / Storefront：展示产品、生成临时访客、发起咨询、传递产品上下文。
- 客服管理中心 `/`：配置客服账号、负责范围、每日上限、咨询额度和统计。
- 客服坐席端 `/agent`：登录、接收自动分配会话、聊天、头像、通知和统计。

`site` 只保存客服系统公网 URL 和验证 Token，并批量同步产品目录。实际访客咨询直接访问本项目，Site 后台不代理聊天，也不参与客服选择。

本项目当前负责：

- 有效咨询接入、幂等、去重、防滥用和 24 小时临时会话；
- 分区 / 分类 / 指定产品的动态客服负责范围；
- 每日接待上限、按量咨询额度和 CTA 两小时绑定约束下的严格轮询；
- 客服坐席实时聊天、图片、已读、输入状态、声音和 Web Push；
- 客服头像自助上传与访客端展示；
- 客服可在坐席工作台维护对外昵称；登录账号保持独立，访客端只展示昵称；
- 会话总数、客服接待分布、产品会话分布、客服每日接待统计和流量凭证；
- 会话、媒体、临时访客及统计数据的自动清理。

本项目不负责：

- 产品内容、产品页面、转化组和站点 CMS；
- 套餐价格、订单、支付、余额和财务结算；
- 人工转接、人工指定其他客服或人工重新分配；
- 长期客户档案、CRM、工单、SLA 或营销自动化；
- 多层企业 RBAC、审批流等个人/小团队不需要的企业功能。

## 2. 技术架构

主要运行在 Cloudflare：

```text
React + Vite
      ↓
Cloudflare Static Assets + Worker / Hono
      ├─ Static Assets：管理端 / 坐席端页面与构建资源
      ├─ D1：账号、会话、消息、路由、统计、额度
      ├─ R2：聊天图片、客服头像
      ├─ Durable Objects：会话和客服实时 WebSocket
      ├─ Rate Limiting：登录、新建会话与媒体突发限制
      ├─ Web Push：访客 / 客服后台通知
      └─ Cron：过期数据与孤立资源清理
```

工程原则：

- Static Assets 保持 Assets-first，Worker 只承担必要 API 与业务边界；
- D1 热路径优先单条 SQL、批量 SQL 和原子更新，避免 N+1 查询；
- 前端能够本地完成的筛选、搜索和草稿不消耗 Worker / D1；
- R2 使用稳定对象键或批量删除，避免无界垃圾对象；
- 不为了理论扩展性提前引入额外服务、消息队列或复杂状态管理；
- CI 预算守卫、格式检查、lint、TypeScript、测试、构建和 Cloudflare dry-run 不通过时不得部署生产。

### 2.1 UI 技术基线

管理中心和客服坐席端共享源码可控的 UI 设计系统：

- shadcn/ui `new-york` 结构：通用组件源码直接保存在仓库；
- Tailwind CSS 4 + Vite Plugin：组件样式、响应式状态和统一设计令牌；
- Radix UI Slot：可组合的基础组件能力；
- Lucide React：管理端和坐席端统一图标来源；
- CSS Variables：颜色、圆角、边框、阴影、焦点环和控件尺寸；
- 业务 CSS：聊天几何、移动端安全区、键盘视口和页面专属复杂布局。

`components.json` 是 shadcn 配置，`src/dashboard/ui/` 是通用组件入口。聊天线程、Visual Viewport、PWA 安全区和弹层几何保持业务 CSS 所有权，不重复造通用控件。

## 3. 管理中心 `/`

管理员通过 Cloudflare Secret `ADMIN_PASSWORD` 登录。

主要能力：

- 创建、编辑、启用或停用客服账号；
- 配置客服登录账号和密码；
- 设置每日接待上限，`0` 表示不限制；
- 启用按量咨询额度，并按 100 / 500 / 1000 或自定义数量追加；
- 查看总额度、已消耗、剩余额度和最近额度变更；
- 设置整个分区、指定分类或指定产品负责范围；
- 查看会话总数、客服接待分布和产品会话分布；
- 在客服账号列表按需查看单个客服的每日接待统计；
- 复制或打开统一客服登录入口。

管理中心只做配置和统计，不代理实际聊天。

## 4. 客服坐席端 `/agent`

所有客服使用统一入口，以各自账号和密码登录；登录后只能读取和操作分配给自己的会话。

主要能力：

- 在线 / 忙碌工作状态展示；
- 新会话、处理中、已关闭状态；
- 未读优先和本地关键词搜索；
- 文字、图片、发送失败重试和本地草稿；
- 消息已读状态和双方输入状态；
- 当前商品封面、名称、分区、分类和商品链接；
- 浏览器后台新消息通知和前台提示音；
- 当前工作台内查看个人统计；
- 设置对外昵称并自助上传、更换和删除客服头像；
- PWA 安装及移动端工作台能力。

坐席端没有人工转接入口。会话归属只由系统统一自动分流逻辑决定，避免人工操作绕过流量额度、每日上限和轮询公平性。

### 4.1 客服资料

登录账号用于认证，对外昵称用于访客展示，两者互相独立。客服可在“客服资料”中修改昵称与头像。

头像上传流程：

```text
选择 JPG / PNG / WebP 原图
→ 浏览器本地读取并居中裁成正方形
→ 最大 512 × 512
→ 优先压缩为 WebP，必要时回退 JPEG
→ 本地预览
→ 客服确认
→ 上传 Worker / R2
```

每名客服只保留一个稳定头像对象 `agent-avatars/<agentId>/current`，更换时覆盖，不累积历史 R2 垃圾。

## 5. Site 接入模型

Site 管理员只配置：

```text
客服系统公网 URL
验证 Token
```

Customer Service 侧对应 Cloudflare Secret 为 `INTEGRATION_VERIFY_TOKEN`。Site 保存的 Token 必须与该 Secret 一致。

验证：

```http
POST {customer-service-public-url}/integration/v1/verify
Authorization: Bearer <token>
Content-Type: application/json
```

产品目录可批量同步。后台录入产品、分区和分类上下文后，管理中心按动态范围配置客服。同步不会变成“一件产品一次 Worker / D1 请求”的逐项模型。

实际访客会话直接调用 Client v1：

```text
/client/v1/conversations
/client/v1/conversations/:id
/client/v1/conversations/:id/messages
/client/v1/conversations/:id/realtime
/client/v1/media/...
```

系统只依赖公网 HTTPS / WSS，不要求与 Site 位于同一个 Cloudflare Account，也不要求固定 Worker 名称或 Service Binding。

## 6. 最终自动分流规则

### 6.1 负责范围

正式路由表为 `agent_routing_scopes`：

- 整个分区：可多选，自动覆盖该分区当前及未来新增产品；
- 指定分类：覆盖选中分区中的指定分类；
- 指定产品：只覆盖明确选择的产品。

没有任何启用范围命中当前产品时，会话保持等待状态，不回退到旧客服分组模型。

### 6.2 候选客服

一个客服必须同时满足：

```text
1. 负责范围命中当前产品
2. 客服账号已启用且登录凭证有效
3. 当日接待数 < 每日接待上限；每日上限为 0 时跳过
4. 新的计费咨询仍有可用咨询额度；未启用额度限制时跳过
```

每日接待上限按 `America/Los_Angeles` 自然日计算。达到上限后，该客服在当天剩余时间退出新的自动分流；次日自然日切换后自动重新进入候选池。

自动分流不读取在线 / 忙碌 / 离线状态。工作状态只用于客服工作台展示和触发等待队列恢复，不改变候选资格。

自动路由不读取在线新鲜度，也不读取心跳时间作为分配依据。

当前进行中会话数和旧的并发上限不参与自动分流。严格轮询只在满足范围、启用、每日上限和咨询额度的候选客服之间执行。

### 6.3 CTA 两小时绑定

同一访客针对同一产品在两小时保护期内再次进入咨询时，系统优先保持原客服绑定。CTA 绑定只在该客服仍满足当前候选资格时生效，不会绕过账号停用、每日接待上限或咨询额度规则。

这不是“新建会话后再优先原客服”的人工补偿逻辑，而是自动路由中的保护约束。

### 6.4 严格轮询

候选顺序：

```text
有效 CTA 两小时绑定客服
→ round_robin_seq 最小
→ 客服 ID
```

`round_robin_seq` 是站点内单调递增的轮询游标。候选查询、每日统计检查和会话写入在 D1 的单条原子更新路径中完成，不对每个候选客服逐项查询。

因此自动分流热路径保持：

```text
范围匹配
→ 启用账号
→ 每日接待上限
→ 咨询额度
→ CTA 两小时绑定
→ 严格 round robin
```

### 6.5 等待队列

没有可用客服时，会话保留为未分配等待状态。登录、心跳或工作状态变化可触发一次有限数量的等待会话恢复，但每条等待会话仍重新进入同一个 `assignConversationAgent()` 规范路由函数。

等待队列不会因为触发恢复的客服在线而优先给该客服，也不会另写一套分流规则。

### 6.6 咨询额度与计数

- 每个会话首次有效接待只生成一条流量凭证；
- 已有凭证的同一会话恢复不会重复扣咨询额度；
- `agent_daily_stats` 按首次接待记录客服当日接待数；
- 每日接待上限控制当日新的自动分配；
- 咨询额度控制累计可购买流量；
- 两者是独立约束，必须同时满足。

## 7. 会话、数据与清理

- 会话生命周期：24 小时；
- 会话过期后不再允许继续聊天；
- 清理 Cron 按小时执行，批量处理到期清理任务；
- 聊天数据按清理策略批量删除，避免每条会话各自触发额外 Worker 请求；
- 统计数据保留 90 天；
- R2 媒体与会话清理由统一清理流程处理；
- 访客端新建会话有防滥用限制，避免短时间无限发起咨询。

## 8. 开发与验证

要求：

- Node.js `>= 22`
- pnpm `>= 11`

常用命令：

```bash
pnpm install
pnpm dev
pnpm preflight
pnpm test
pnpm build
pnpm verify
```

`pnpm verify` 顺序执行：

```text
guardrails
→ prettier --check
→ eslint
→ TypeScript
→ 本地 D1 migrations
→ tests
→ UI + Worker build
→ wrangler deploy --dry-run
```

生产部署：

```bash
pnpm deploy:cloudflare
```

部署会先执行远程 D1 migration，再运行 `wrangler deploy --keep-vars`。GitHub Actions 的 `CI and Deploy` 是生产主路径；不要通过提高 bundle / CSS / workflow 预算来绕过守卫。

## 9. Cloudflare 资源

核心绑定：

- D1：客服、会话、消息、路由、统计、额度；
- R2：聊天媒体和客服头像；
- Durable Objects：会话与客服 inbox 实时连接；
- Web Push：后台消息通知；
- Cron：清理和维护任务；
- Secrets：管理员密码、Site 集成验证 Token、Web Push 等敏感配置。

R2 自定义域名不作为业务逻辑写死值。媒体读取地址应由部署/后台配置决定。

## 10. 设计原则

这个项目面向个人和小团队，优先级始终是：

```text
功能稳定
→ 分流规则明确且可测试
→ Workers / D1 / R2 请求成本可控
→ UI 简洁直接
→ 仓库和 CI 保持干净
```

不增加与流量接待核心无关的企业级功能，不保留已经取消的人工转接等死功能，也不维护与正式路由并行的第二套分流逻辑。
