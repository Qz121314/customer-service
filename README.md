# Customer Service

面向个人运营者和小团队的轻量客服坐席与咨询流量分发系统，独立于 [`Qz121314/site`](https://github.com/Qz121314/site) 开发和部署。

生产地址：<https://customer-service-app.fcqz121314.workers.dev>

> 本项目不是长期 CRM。核心职责是接收有效咨询、按最终分流规则分配给客服坐席，并提供 24 小时临时聊天接待和必要统计。

## 1. 最终系统边界

完整链路：

```text
Site / 产品页
→ 生成临时访客与唯一 sourceHandoffId
→ customer-service 校验产品上下文、幂等和防滥用
→ 按负责范围、账号启用状态、在线状态、每日接待上限、剩余额度筛选坐席
→ CTA 两小时保护
→ 严格轮询选择坐席
→ D1 原子分配
→ 客服坐席工作台接待
→ 生成可统计、可对账的有效流量凭证
```

边界固定如下：

- Site / Storefront：展示产品、生成临时访客、发起咨询、传递产品上下文。
- 客服管理中心 `/`：配置客服账号、负责范围、每日接待上限、按量额度和统计。
- 客服坐席端 `/agent`：登录、接收已分配会话、聊天、昵称、头像、通知和 PWA。

`site` 只保存客服系统公网 URL 和验证 Token，并批量同步产品目录。实际访客咨询直接访问本项目；Site 后台不代理聊天，也不参与坐席选择。

产品目录以 Site 的 `/integration/v1/verify` 全量同步结果为权威。访客请求只提交 `product.id`；客服系统从 `product_catalog` 读取标题、链接、图片、分区和分类，不能通过访客请求覆盖目录或重新启用已禁用产品。

### 明确不做

- 人工转接、人工重新排队、转接目标选择；
- 长期客户档案、CRM、工单、SLA、营销自动化；
- 套餐价格、订单、支付和财务结算；
- 多层企业 RBAC、审批流等个人或小团队不需要的复杂功能。

**人工转接已经从产品定义中删除。** 运行时代码、API、实时事件、前端入口和测试都不应再依赖人工转接概念。

## 2. 最终分流规则（Routing Contract）

本章是客服系统分流逻辑的最终业务规格。**README、运行时代码、数据库约束和行为测试必须以本章为同一事实来源，不允许出现第二套分流解释。**

### 2.1 先区分“新流量分配”和“已有会话归属”

这是整个分流系统最重要的边界：

- **新流量分配**：一个尚未分配客服的有效会话，需要决定首次接待客服。只有这种情况才进入候选筛选、CTA 亲和和严格轮询。
- **已有会话归属**：会话已经分配给某个客服。客服后来切换忙碌、离线、账号停用、达到每日上限或购买额度耗尽，都**不会把这个已有会话自动重新分配给其他客服**。
- 忙碌、离线、停用、达到每日上限和额度耗尽控制的是“还能不能接新的自动流量”，不是“还能不能保留已经接到的会话”。
- 客服账号不能在仍有进行中会话时永久删除；管理员应先停用账号并处理完会话，再执行永久删除。这样不会产生半成功重分配或隐藏等待会话。

因此，任何地方出现“客服不接待”的描述时，都必须明确它指的是：**不接收新的自动分配**，而不是强制转走已有会话。

### 2.2 负责范围如何命中

正式路由表为 `agent_routing_scopes`。

支持三种范围：

- 整个分区：可多选，自动覆盖该分区当前及未来新增产品；
- 指定分类：覆盖选中分区中的指定分类；
- 指定产品：只覆盖明确选择的产品。

范围命中规则是 **OR**：客服只要有任意一个已启用范围命中当前产品，就通过“负责范围”这一关。

例如同一个客服既负责 `west` 分区，又单独配置了 `product-a`，当 `product-a` 属于 `west` 时，该客服仍然只算 **1 个候选客服**，不会因为同时命中两个范围而获得双倍权重或额外轮询机会。

三种范围只决定“是否有资格”，不提供优先级：

```text
产品范围 > 分类范围 > 分区范围   ❌ 不存在这种优先级
命中任意有效范围               ✅ 进入下一步资格检查
```

没有任何启用范围命中当前产品时，本次创建直接返回管理员配置的无客服提示语，不保留等待会话、不回退到旧客服分组模型，也不会随机分给无负责范围的客服。

### 2.3 新流量接待资格：必须同时满足全部条件

一个尚未分配的新会话，只允许分给同时满足以下条件的客服：

```text
1. 客服账号已启用
2. 客服本人当前状态 = online
3. 至少一个已启用负责范围命中当前产品
4. 已配置可登录 username
5. 已配置 password_hash
6. 当日首次有效接待量未达到 dailyConversationLimit
7. 如果启用了购买额度限制，则 trafficQuotaUsed < trafficQuotaTotal
```

其中：

- `status = online` 是唯一的在线业务判断；
- `last_seen_at` 只用于后台展示最后活动时间、调试、日志和运维分析，不参与新会话分流或已有会话复用资格；
- heartbeat 新鲜度、WebSocket 连接、标签页可见性和浏览器活动均不参与分流；
- `dailyConversationLimit = 0` 表示每日不限；
- 购买额度限制未启用时，不检查总额度；
- 每日接待上限和购买额度是两个独立门槛，普通新流量必须同时通过；
- 任意一个条件不满足，该客服就不进入本次会话的候选集。

客服业务状态只按以下操作切换：

```text
登录成功       → online
点击 Busy      → busy
Busy 切回在线  → online
正常 Logout    → offline
```

系统不根据浏览器关闭、标签页可见性、WebSocket 或 heartbeat 新鲜度自动改写上述业务状态。

#### 接待 / 不接待决策表

| 客服当前情况                                                    | 接收新的自动流量 | 已分配会话归属是否保留 | 说明                                       |
| --------------------------------------------------------------- | ---------------- | ---------------------- | ------------------------------------------ |
| 已启用 + 在线 + 范围命中 + 有登录凭证 + 未达日上限 + 有可用额度 | 是               | 是                     | 正常候选客服                               |
| 忙碌 `busy`                                                     | 否               | 是                     | 忙碌只停止新流量，不转走已有会话           |
| 离线 `offline`                                                  | 否               | 是                     | 离线期间不接新流量，已有归属不变           |
| 管理员停用账号                                                  | 否               | 是                     | 停用关闭新自动分流资格，不等于删除历史会话 |
| 负责范围不命中当前产品                                          | 否               | 是                     | 不能因为其他产品有权限而接当前产品         |
| 没有可登录账号或密码                                            | 否               | 是                     | 不允许把新流量分给无法实际登录接待的坐席   |
| 达到每日接待上限                                                | 否               | 是                     | 下一业务日恢复新流量资格                   |
| 购买额度启用且额度耗尽                                          | 否               | 是                     | 补充额度后恢复新流量资格                   |
| 同时命中多个负责范围                                            | 最多算 1 个候选  | 是                     | 不增加权重、不重复进入候选列表             |

### 2.4 一次新咨询的固定决策顺序

任何新咨询都必须严格按照以下顺序处理，后面的规则不能越过前面的规则：

```text
A. 网络重试 / 幂等重放
   sourceHandoffId 或 clientMessageId 已处理
   → 仍绑定原会话，不创建第二个会话，不重新轮询
   → 活动会话的原客服仍为 enabled + online 时返回原会话
   → 原客服 busy / offline / disabled 时返回当前无可用客服，原会话归属不变

B. CTA 两小时活动会话复用
   同一 site + visitor + product 存在两小时内仍活动的 open / pending 会话
   → 原客服 is_enabled = 1 且 status = online 时直接复用
   → 不检查 last_seen_at、heartbeat、WebSocket 或浏览器活动
   → 原客服 busy / offline / disabled 时返回当前无可用客服，不自动转给其他客服

C. 新会话候选筛选
   没有可直接复用的活动会话
   → 根据账号、状态、范围、登录凭证、日上限、购买额度生成候选集

D. CTA 两小时客服亲和
   两小时内最近会话已经关闭，但曾有原客服
   → 只有原客服当前仍属于合格候选时，才优先选择原客服
   → 原客服当前不合格时，亲和自动失效并进入普通轮询

E. 站点级全局严格轮询
   没有有效亲和客服
   → 从当前 site 的全局轮询游标之后选择第一个合格客服

F. D1 原子写入
   成功选择客服
   → 原子写入 assigned_agent / assigned_at
   → 同一次成功分配推进站点级全局轮询游标

G. 无合格客服
   → 删除本次尚未分配的临时会话和对应创建占用
   → 返回 503 / NO_AGENT_AVAILABLE 和管理员配置的普通文本或 Markdown 提示语
   → 不建立等待队列，也不在客服上线、补充额度或关闭其他会话后自动恢复
   → 不推进任何轮询游标
```

最终优先级只有这一条：

```text
幂等重放
> 两小时活动会话直接复用
> 两小时有效客服亲和
> 站点级全局严格轮询
> 无客服则返回配置提示语且不创建会话
```

不得新增“最近在线优先”“最少会话优先”“管理员标记优先”“额度更多优先”“忙碌客服兜底”等隐藏优先级。

### 2.5 站点级全局严格轮询

`routing_round_robin_cursors` 按：

```text
site_id
```

为每个站点保存唯一的 `last_agent_id`。

**同一个 site 的所有正常新会话共享同一个轮询游标。** 产品、分区和分类只决定当前会话有哪些客服有资格接，不再拥有自己的 Round Robin 游标，也不能让不同产品各自从第一位客服重新开始。

全局客服按稳定的客服 `id` 升序形成环形位置：

```text
agent-a → agent-b → agent-c → agent-d → agent-a → ...
```

每一条新会话先根据当前产品 / 分区 / 分类和其他资格条件筛选合格客服，再相对于站点全局 `last_agent_id` 寻找下一个合格客服。

选择规则：

1. 找到当前 site 的全局 `last_agent_id`；
2. 从它之后寻找第一个对当前会话合格的客服；
3. 如果后面的客服都不合格或已经到 ID 顺序末尾，则从最小客服 ID 环回继续找；
4. 只有真正成功写入一次新的客服分配，才把全局游标更新为实际接待客服；
5. 被跳过的客服不会推进游标；
6. 没有客服可分配时不会推进游标；
7. 客服恢复资格后按自己在固定 ID 环中的自然位置重新加入，不获得“补偿流量”或“追赶优先级”。

即使全局游标指向的客服当前已经忙碌、离线、停用、额度耗尽、范围移除甚至被删除，游标仍然只是一个站点级环形位置标记。系统继续寻找 `id > last_agent_id` 的第一个当前合格客服，找不到再从最小 ID 环回，不因为候选集发生变化而重置公平顺序。

#### 示例 1：不同产品共享同一个轮询顺序

假设 A / B / C 都能接当前进入的这些产品，会话依次来自：

```text
P1 / P2 / P3 / P1 / P4 / P2
```

连续新会话应为：

```text
P1 → A
P2 → B
P3 → C
P1 → A
P4 → B
P2 → C
```

产品变化不会创建新的轮询起点。

#### 示例 2：当前产品范围导致中间客服被跳过

全局顺序：

```text
A → B → C → D → A
```

上一位是 C，而当前产品只有 A / B 有资格：

```text
D → 当前产品范围不命中，跳过
A → 合格，分配给 A
```

于是全局游标更新为 A。产品范围只过滤候选人，不创建产品自己的游标。

#### 示例 3：轮到 B 时 B 进入忙碌

上一位是 A，当前：

```text
A = online
B = busy
C = online
```

下一次：

```text
跳过 B → C
```

再下一次：

```text
C 后环回 → A
```

如果此时 B 恢复 online，由于上一位是 A：

```text
下一次自然轮到 B
```

B 不会因为刚才被跳过而额外连续获得多笔流量。

#### 示例 4：达到每日上限或额度耗尽

假设当前会话的合格范围覆盖 A / B / C，上一位 = A，B 已达到每日上限，C 正常：

```text
A → 已接上一笔
B → 达到上限，跳过
C → 分配
```

B 下一业务日恢复后，只按自己的自然环形位置重新加入；系统不补发昨天错过的流量。

### 2.6 CTA 两小时保护与普通轮询的关系

服务端以：

```text
siteId + visitorId + productId
```

识别同一产品咨询。

目标固定为：**同一访客在两小时窗口内针对同一产品，不因为重复点击 CTA 被随机分给不同客服，同时不能让已失去接待资格的旧客服强行抢占新的独立会话。**

分两种情况：

#### 情况 A：两小时内原会话仍是活动会话

如果最近会话仍满足：

```text
status = open / pending
未超过会话生命周期
last_message_at 仍在两小时窗口内
```

则直接复用原会话：

- 不创建新会话；
- 保留原 `assigned_agent`；
- 原客服必须仍为 `is_enabled = 1 AND status = 'online'`；
- 不检查原客服的 `last_seen_at` 新鲜度、heartbeat 或 WebSocket 状态；
- 不重新轮询；
- 不重复消耗访客创建限制；
- 不重复消耗每日接待次数；
- 不重复消耗购买额度；
- 原客服当前切换 busy / offline / disabled 不会导致这条已有会话被自动转给别人；重复 CTA 会返回当前无可用客服，原会话归属保持不变。

#### 情况 B：两小时内最近会话已经关闭

此时允许创建新的会话，但最近原客服形成临时亲和：

- 原客服如果当前仍满足全部新流量资格，则优先分给原客服；
- 原客服如果已经 busy、offline、disabled、范围不匹配、达到日上限或额度耗尽，则不能依靠两小时亲和绕过资格门槛；
- 原客服不合格时直接按站点级全局严格轮询选择其他合格客服；
- 两小时窗口外不再提供亲和优先级。

不同产品的两小时保护彼此完全隔离。

### 2.7 每日接待上限

**每日接待上限只限制新的首次有效流量。**

规则固定为：

- `dailyConversationLimit = 0` 表示不限；
- `dailyConversationLimit > 0` 时，当天首次有效接待数量达到该值后，该客服立即退出普通新流量候选集；
- 达到上限的客服不会占用本次轮询位置，也不会因为被跳过而推进轮询游标；
- 其他仍符合条件的客服继续按站点级全局严格轮询接收新流量；
- 所有匹配客服都达到上限或其他资格不满足时，本次创建返回 `NO_AGENT_AVAILABLE`，不保留等待会话；
- 下一业务日自动恢复每日接待资格，不需要管理员手动清零；
- 业务日统一按 `America/Los_Angeles` 自然日计算；
- 同一个已存在会话继续聊天不会重复计算每日接待；
- 历史或异常的未分配会话不会因为新一天到来而自动恢复分配；新 CTA 始终按当前资格发起新的创建尝试。

### 2.8 购买额度边界

购买额度只限制新的可计费首次接待：

```text
额度限制关闭
→ 不检查 trafficQuotaTotal / trafficQuotaUsed

额度限制开启且 used < total
→ 可以继续接普通新流量

额度限制开启且 used >= total
→ 不接普通新流量
```

购买额度只在新会话首次成功分配时扣减一次。已分配会话的重试、重连和继续发消息不重复扣费。历史或异常的未分配记录不是可恢复的流量：访客 API 不返回、不允许追加消息，也不会重新分配它。

### 2.9 无客服响应与无等待队列

当新会话创建时没有任何合格客服：

```text
HTTP 503
error.code = NO_AGENT_AVAILABLE
error.message = 管理员配置的提示语
error.format = plain / markdown
```

规则固定如下：

- 不向访客返回 `waiting` 会话；
- 不保留本次未分配的会话、消息、source handoff 占用或创建额度占用；
- 客服登录、切回在线、管理员启用账号、补充额度或客服关闭其他会话时，都不会扫描或恢复旧等待记录；
- 访客稍后再次点击 CTA 时，按当时最新资格重新发起一次创建；
- 无候选结果不推进站点级全局轮询游标；
- 管理员可在管理中心配置普通文本或 Markdown 提示语，访客端按返回的 `format` 安全渲染。

### 2.10 并发、幂等和游标一致性

为了避免两个访客同时发起咨询时产生重复分配或破坏轮询，以下约束是强制要求：

- 同一个 `sourceHandoffId` 永远只能绑定同一条会话记录；
- 同一个 `clientMessageId` 的重试不能生成重复消息或第二次创建；
- 幂等重试只复用原会话，不重新分流；活动会话原客服当前不可用时，响应可以反映最新的无客服状态；
- 同一个会话只能从“未分配”成功进入一次首次分配；
- 候选选择与 `assigned_agent` 写入必须保持在 D1 原子写入路径中；
- 站点级全局轮询游标只能随真实成功的客服分配推进；
- 失败、重试、无候选和活动会话直接复用都不能额外推进游标；
- 同一站点并发创建时必须以数据库最终成功写入顺序保持全局轮询一致性，不能让两个并发请求因为读取同一个旧游标而都占用同一个轮询位置。

### 2.11 明确禁止出现的分流冲突

以下行为一律视为业务缺陷：

- `busy` 客服仍收到新的自动流量；
- `offline` 客服仍收到新的自动流量；
- 管理员停用的客服仍收到新的自动流量；
- 不负责该产品的客服因为“没有其他人”而被兜底分配；
- 一个客服因为同时命中多个负责范围而在候选列表出现多次；
- 达到每日上限或额度耗尽的客服仍收到普通新流量；
- 不同产品各自维护独立轮询游标或各自从第一位客服重新开始；
- 被临时跳过的客服恢复后获得补偿式优先级；
- 无人可接时强行分配给不合格客服，或创建可见的等待会话，而不是返回配置提示语；
- 活动会话的重复 CTA 被新建成第二个会话并重新随机分流；
- 已关闭会话的两小时亲和绕过 busy / offline / disabled / 日上限 / 额度等资格门槛；
- 访客读取、发消息、幂等重试或客服资格变化时恢复历史 / 异常未分配会话；
- 客服上线、额度恢复或状态变化时重新引入等待队列扫描；
- 没有真实成功分配却推进轮询游标。

## 3. 咨询额度

额度模型：

```text
管理员为指定客服追加已购买咨询次数
→ 首次有效接待扣 1
→ 剩余为 0 后停止接收新的付费流量
```

计算：

```text
剩余额度 = max(总额度 - 已消耗, 0)
```

规则：

- 额度限制未启用时，不以总额度筛选候选；
- 额度启用且剩余额度为 0 时，停止新的首次有效分配；
- 一次有效咨询只生成一次不可变流量凭证；
- 额度追加使用唯一 `trafficQuotaRequestId` 保证幂等；
- 关闭额度限制不会清除历史额度和消耗记录；
- 每日接待上限与购买额度是两个独立条件，新流量候选必须同时满足二者。

## 4. 管理中心与坐席端

客服管理中心 `/` 只负责配置和统计：

- 创建、编辑、启用、停用或删除客服账号；
- 配置客服登录账号和密码；
- 设置仅管理员可见的客服编号标记；
- 设置分区、分类或指定产品负责范围；
- 设置每日接待上限；
- 启用按量额度并追加咨询次数；
- 查看总额度、已消耗、剩余额度和最近额度变更；
- 查看会话总数、客服接待分布、产品会话分布；
- 客服接待分布使用管理员标记，不显示客服昵称；
- 查看单个客服自然月每日接待统计；
- 复制或打开统一客服登录入口。

客服坐席端 `/agent` 只操作分配给自己的会话：

- 在线或忙碌工作状态；
- 新会话、处理中、已关闭状态；
- 未读优先和本地关键词搜索；
- 文字、图片、发送失败重试和本地草稿；
- 在坐席设置中维护 SMS、WhatsApp、Telegram 或网站名片与可选预设话术，并从聊天“+”和首次问候语中引用；
- 消息已读状态和双方输入状态；
- 商品上下文；
- 新会话系统通知和工作台内提示音；
- 个人统计；
- 对外昵称和头像；
- PWA 安装与移动端安全区适配。

名片属于长期准备项：坐席在设置菜单中通过紧凑下拉选择 SMS、WhatsApp、Telegram 或网站，填写名称和号码、用户名或链接；SMS 使用苹果 Messages / iMessage 绿色消息图标样式，WhatsApp 和 Telegram 使用各自官方品牌标志与品牌色，自定义上传只作为覆盖扩展。SMS、WhatsApp 和 Telegram 可选填预设话术，网站名片不带预设话术。聊天“+”菜单和首次问候语只引用已保存的名片，不在发送时临时创建。访客点击 SMS 必须打开 `sms:` 短信界面，不能生成 `tel:` 拨号链接；WhatsApp、Telegram 和网站分别使用对应的安全链接。名片发送时固化为消息快照，之后编辑、删除预设或替换图标都不能改写历史消息。聊天输入框仍可直接选择并发送一次性图片。

账号“停用”只关闭新的自动分流资格，不等于禁止登录。停用客服仍可登录工作台、切换在线/忙碌、处理原有会话和使用个人设置；重新启用后，只有其本人状态为在线时才恢复接收新会话。

客服正常 Logout 会删除该客服的全部登录会话并设置为 `offline`；永久删除仍有进行中会话的客服会被拒绝，避免清空归属后产生隐藏会话或假重分配。

这里的两种提醒都属于客服坐席工作台：工作台切换到其他应用或手机锁屏时，由“新会话通知”通过系统通知提醒；工作台正在屏幕上使用时，由“工作台提示音”在收到新分配会话或访客新消息时响铃。Android 可在支持 Web Push 的浏览器或已安装 PWA 中开启系统通知。iPhone / iPad 需要先把客服坐席添加到主屏幕，再从桌面图标打开并由客服主动授权通知。系统通知是否发声最终由 iOS / Android 的通知声音设置控制。

**坐席端不存在人工转接按钮、转接菜单或转接 API。** 客服昵称和头像由客服维护并展示给访客；用户名只用于登录坐席工作台；客服标记只供管理员识别，不进入坐席端或访客端 API。

## 5. 会话生命周期与防滥用

24 小时临时会话规则：

- 生命周期从创建时固定计算 24 小时；
- `conversations.expires_at` 是运行时权威到期字段；
- 新消息不续期；
- 到期后删除会话、消息、媒体记录和相关 R2 对象；
- 无会话的过期临时访客随后删除；
- Worker Cron 每个整点执行一次有界清理。

防滥用规则：

- Cloudflare Rate Limiting 先拦截短时间突发创建；
- 单个 `visitorId` 在 24 小时活动窗口最多成功创建 10 个会话；
- 同一来源指纹在 24 小时活动窗口最多成功创建 20 个会话；
- `sourceHandoffId` 和 `clientMessageId` 提供幂等保护；
- 两小时 CTA 复用不会重复消费创建次数。

## 6. 统计

统计保留 **90 个自然日**，业务日按 `America/Los_Angeles` 计算。

管理中心只保留三类核心统计：

1. 会话总数；
2. 客服接待数分布；
3. 产品会话数分布。

单客服统计按自然月显示每日接待量。

统计与短期聊天数据分离。24 小时会话删除后，90 天统计和不可变流量凭证仍可用于对账。

## 7. 技术与成本原则

运行栈：

```text
React + Vite
Cloudflare Static Assets + Worker / Hono
D1
R2
Durable Objects + WebSocket Hibernation
Rate Limiting
Web Push
Cron
```

成本原则：

- 静态 UI 优先由 Static Assets 提供；
- D1 热路径优先单条 SQL、批量 SQL 和原子更新；
- WebSocket `ping/pong` 由 Durable Object 运行时自动响应，不唤醒对象或写入 D1；
- 双方已读状态使用会话级游标，每次确认最多更新一条会话记录，API 继续返回逐消息已读字段；
- 消息发送不重复刷新访客活跃时间，不为高频变更字段维护无查询收益的索引；
- 不做按客服逐项请求或重复读取；
- 搜索、筛选、草稿和纯 UI 状态尽量在浏览器本地完成；
- 产品目录同步使用一次请求和批量 D1 处理；
- 无合格客服时清理临时创建记录并直接返回配置提示语，不维护等待队列或恢复扫描；
- 同一访客的新 CTA 使用固定的两小时创建 claim；并发请求最终只保留一条会话和一笔额度凭证；
- 会话创建成功后，实时广播属于通知副作用；广播暂时失败不会覆盖数据库中的成功结果；
- R2 使用稳定对象键和有界批量清理；
- 不为了理论扩展性增加额外服务、队列或复杂状态管理。

## 8. UI、PWA 与媒体

管理中心和坐席端共享项目内的统一 UI 设计系统：

- shadcn/ui `new-york` 结构；
- Tailwind CSS 4；
- Radix UI Slot；

坐席端 PWA：

- Manifest `id`、`start_url`、`scope` 限定在 `/agent`；

R2：

- 聊天图片随会话生命周期清理；

- 正式环境优先浏览器直传 R2，减少 Worker 数据路径。

**测试业务行为，不测试源码写法。**

允许验证：

- D1 数据变化；

- README 文案；
- 某段 SQL 必须以固定文本出现。

路由行为测试至少覆盖：

```text
同一站点连续新会话保持严格全局环形轮询顺序

dailyConversationLimit = 0 时不限

全部新流量候选达到上限时返回 NO_AGENT_AVAILABLE 且不创建等待会话
下一业务日重新获得每日接待资格
活动会话在 CTA 两小时内直接复用原会话和原客服
幂等重试不创建第二个会话，活动会话原客服不可用时返回 NO_AGENT_AVAILABLE
已关闭会话在 CTA 两小时内只对仍合格的原客服提供亲和优先级
亲和客服 busy / offline / disabled / 日上限 / 额度耗尽时回退全局严格轮询
```

### 名片与迁移测试注意事项

名片功能同时跨越坐席设置、聊天与首次问候语引用、Worker API、D1 migration、R2 图标和访客端链接协议，修改时必须一起核对，不能只验证设置界面。

- Node 行为测试通过 ESM 直接加载部分 `.ts` 模块。被测试模块新增相对 TypeScript 依赖时，必须保证 Node 能解析传递依赖；不能只依赖 Vite、TypeScript Bundler 或 Wrangler 自动补扩展名。本项目对这种测试可达依赖使用显式 `.ts` 后缀，并由 `tsconfig.worker.json` 的 `allowImportingTsExtensions` 配合无输出类型检查。
- `node:sqlite` 的 `.all()` 返回无原型行对象。与普通对象字面量做 `assert.deepEqual` 前，先使用 `{ ...row }` 转换成普通对象；字段和值仍须完整断言，不能通过放宽或删除迁移测试换取 CI 通过。
- 新 migration 必须从上一版 schema 准备历史数据，再单独应用新 migration 验证转换结果；同时还要通过全量本地 D1 migration，禁止修改、重写或删除已经上线的 migration。
- 名片预设与消息快照用途不同：预设可以编辑或删除，已发送快照必须不可变；自定义图标被替换或移除后，历史快照引用的 R2 对象不能被同步删除。
- SMS、WhatsApp、Telegram 的官方渠道 SVG 集中放在 `public/icons/contact-card-*.svg`。不要换成 Lucide 通用图标，也不要在组件或 CSS 中复制内联 SVG；渠道选择仍保持单个紧凑下拉框，避免恢复成占高的多按钮网格。
- 移动端名片弹窗保持“固定标题 + 单一纵向正文滚动 + 横向已保存名片 + 表单内固定主操作”。禁止给已保存名片再套纵向滚动容器，否则保存后保留的 `scrollTop` 会让名片行被截断；保存成功必须回到正文顶部，编辑时必须把表单滚动到可见区域。`test/agent-card-icon-browser-smoke.spec.mjs` 必须继续纳入 CI 的 Agent Chromium smoke，验证 390×844 视口几何与横向滑动。
- PR 测试失败时，后续 Build、Worker bundle、浏览器 smoke 和 Cloudflare 部署会被跳过。排查时先看第一个失败步骤，不要把“未执行部署”误判为 Cloudflare 故障。
- 合并前按 `pnpm verify` 验证完整仓库；名片 UI 还必须通过 Agent Chromium smoke。只有 PR 全绿后才能合并，最终完成标准仍是 main 部署成功并通过 production protocol smoke。

### 空 Cloudflare 账号一键部署

仓库中的 `wrangler.jsonc` 只声明可移植的资源名称和绑定，不保存任何 Cloudflare 账号专属 D1 UUID。复制仓库到新的 GitHub 仓库后，只需要添加两个 Repository Secrets：

```text
CLOUDFLARE_ACCOUNT_ID
CLOUDFLARE_API_TOKEN
```

API Token 至少需要目标账号的以下权限：

```text
Workers Scripts: Edit
D1: Edit
Workers R2 Storage: Edit
```

Cloudflare 的 R2 是唯一的账号级前置条件：全新账号必须先在 Dashboard 的 `Storage & databases → R2` 完成一次 R2 subscription 开通。R2 有免费用量，但 Cloudflare 要求先完成该 checkout；这个账号动作不能由 GitHub Actions 或普通 API Token 代替。除此之外，不需要提前创建 Worker、D1、R2 Bucket 或 Durable Object。

第一次从 GitHub Actions 手动运行 `CI and Deploy`，部署流程会按资源名称执行幂等引导：

```text
复用已有 D1 / R2，缺失时创建
→ 应用全部 D1 migrations
→ 部署 Worker + Durable Object
→ 绑定 Rate Limit + Cron
→ 上传 Static Assets
→ 执行生产协议 Smoke
```

同一个流程同时兼容当前已经运营的 Cloudflare 账号：`customer-service-db` 和 `customer-service-media` 已存在时只会复用，不会删除、清空或新建替代资源；Worker Secret 也不会因部署而被删除。

首次部署成功后，在 Cloudflare Worker 中人工设置：

```text
ADMIN_PASSWORD
INTEGRATION_VERIFY_TOKEN
```

Worker 自定义域名按实际运营域名人工绑定。R2 自定义域名保持可选；聊天媒体桶默认保持私有，不需要为一键部署绑定公开域名。

Pull Request 全绿只代表可以合并。真正发布完成必须同时满足：

```text
main CI 全绿
Cloudflare production deploy 成功
production protocol smoke 成功
```

## 11. Migration 原则

已经上线的 migration 不改名、不重写、不删除。

历史结构和已经删除的历史功能只通过新的前向 migration 收口。运行时代码只依赖最终 schema，不因为旧 migration 中曾经存在某功能就保留对应运行时代码。

## 12. 收口原则

项目进入收口阶段后默认执行：

1. 功能稳定优先于功能数量；
2. 最终业务规则以 README 和行为测试为准；
3. README、测试和实现必须一致；
